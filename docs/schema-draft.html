Equipment Acquisition Schema

Nine tables for the Equipment Acquisition Recording System — eight base tables plus one denormalized read model — sized for a large organization (25,000 AcquisitionRequest rows, lowered from an original 100k+ target to keep a reviewer's first run reasonable) so the department-spend report needs a real, measurable optimization rather than a LINQ one-liner. Targets SQL Server; one table (MenuItem) is standalone — the full-CRUD React showcase, unconnected to the acquisition domain below.

01 Overview

Four reference tables (Department, EquipmentCategory, Vendor, Employee) feed two transactional tables (AcquisitionRequest, PurchaseOrder) that join 1:1 on AcquisitionRequestId — that join is the one the department-spend report aggregates across. Asset sits downstream of PurchaseOrder, and carries an independent relationship back to Department for whichever department currently holds it, separate from whichever department originally requested it. A separate, self-referencing MenuItem table sits outside this domain entirely — it's the one entity with full React CRUD (List/Create/Edit/Delete), while everything else here is exercised through the API only.

Alongside those eight sits EquipmentAcquisitionDetailCache — a second standalone table, unconnected to the graph above by any foreign key in either direction. It holds one flat row per request with values copied from Department, EquipmentCategory, both Employees, PurchaseOrder and Vendor, so a detail read is a single-key lookup that joins nothing and computes nothing. It is rebuildable by definition, and deliberately not what the department-spend report reads from.

12 Design decisions

Frontend scope: React CRUD on MenuItem only

The frontend is React + Material UI, built as separate per-page bundles (Webpack, multiple entries) rather than one SPA — a nav bundle rendering the dynamic menu, and a menu-admin bundle for full List/Create/Edit/Delete on MenuItem. It replaces a real legacy pattern — a hardcoded Web.sitemap + asp:Menu, each page loading its own app.js — with a menu that's data, using the same one-bundle-per-page shape. Every other table here (requests, assets, the report) is exercised through the API and Swagger, not a React page.

The detail cache backs reads, and never the report

EquipmentAcquisitionDetailCache flattens five tables into one row per request so detail and grid reads don't re-join them at 25,000 rows. Two rules keep it honest. First, it is write-only from the refresh path and read-only everywhere else — no business logic branches on a cached value, so a stale row degrades a display, never a decision. Second, the department-spend report does not touch it: pointing the report at a precomputed table would quietly replace the measured naive-vs-optimized story with "I precomputed it," which is the one thing the assessment is actually scoring. The base tables plus the composite index remain the report's path.

The cache stores Status, contradicting the table above it — knowingly

AcquisitionRequest.Status is deliberately derived rather than stored, on the grounds that a stored copy can drift. The cache stores it anyway, because a projection that still needs a CASE over two date columns on every read has given back part of what it was built for. The contradiction is accepted rather than resolved, and bounded by the read-only rule above. Worth removing if the refresh path proves harder to keep correct than the CASE was to compute — that trade is the whole argument.

Standalone: value copies, and not one foreign key

Every *Id on the cache — AcquisitionRequestId included — is a plain column, not a reference. Real FKs would point Restrict delete paths from six directions into a table whose defining property is that it can be truncated and rebuilt, and would make every write to the base tables pay constraint-checking cost that this table exists to avoid. The reading side is the whole argument: a detail view becomes one key lookup returning one row, with no join, no aggregate and no CASE — the work happens once at refresh time instead of on every read.

What that costs: nothing in the database keeps this table honest. Delete a request and its cache row survives as an orphan; rename a department and every row naming it goes stale. That is not a gap in the schema — it is the schema deliberately declining a job, and handing it to an orchestration layer built for exactly that: a queue table written in the same transaction as every business write, and a background worker that resolves each signal and rebuilds only the affected rows (full design in table-design.md). RefreshedAt exists so staleness can at least be measured rather than assumed.

Employee is intentionally minimal

Just Id, DepartmentId, FullName, JobTitle — no auth, no employment status. It exists to replace the earlier plain RequestedBy string with a real relationship, wired only into AcquisitionRequest's two employee FKs. Asset's custodian deliberately stays at the department level rather than also gaining an Employee FK — that's a separate decision this project doesn't need to make.

AcquisitionRequest.Status is derived, not stored

Computed from ApprovedDate/RejectedDate rather than kept as its own column — one less field that can drift out of sync with the dates that actually drove the state change.

Asset.Status stays a real column

Unlike the request, an asset's lifecycle isn't one-way — it can cycle Assigned → Maintenance → Assigned more than once, which a set of nullable "state date" columns can't represent cleanly. Dates work for a linear flow; an enum for a cyclical one.

PurchaseOrder.TotalCost is stored, not computed on read

At 25,000 rows, the report sums cost across every matching row. Storing Quantity × UnitCost at write time avoids a multiply-and-sum over the full row set on every report run — kept in sync in the service layer, not a DB trigger.

Composite index the naive report query runs without

(DepartmentId, EquipmentCategoryId, RequestDate) on AcquisitionRequest. The naive version of the report is deliberately measured before this index exists, so the before/after numbers in the write-up are real, not staged.

Mutual exclusivity enforced at the DB level

CK_AcquisitionRequest_MutuallyExclusiveDates — a request is approved or rejected, never both (confirmed: no reversal case). A check constraint, not just an application-layer guard, so the rule holds regardless of which code path writes the row.
