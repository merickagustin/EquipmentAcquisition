Equipment Acquisition Plan

A sample app built to demonstrate three things side by side: an optimized SQL Server stored procedure, a layered .NET Web API, and a React + Material UI frontend — for a C#/.NET technical assessment. The timeline below is the original plan as scoped; Status reflects what's actually been built, which has grown past it.

01 Overview

The premise: equipment acquisition tracking for a large organization — requests, approvals, purchase orders, and asset assignment across departments — sized to 25,000 AcquisitionRequest rows so the reporting query needs a real, measurable optimization rather than a LINQ one-liner. Lowered from an original 100k+ target to keep a reviewer's first run reasonable — a deliberate trade against how dramatic the naive-vs-optimized gap will look. Full detail lives in three companion docs, linked under Schema & deployment.

Scope boundary, as originally stated: only MenuItem would get a full frontend (List/Create/Edit/Delete in React); everything else exercised through Swagger, not a page. That boundary has since moved — see Status — but the reasoning behind it hasn't: effort stayed weighted toward the backend (schema, the optimized proc, the layered API) first, with the frontend build-out happening only after that foundation was complete and verified.

Two-phase build, not one atomic push. Foundation first: schema, seeded data, the stored-proc optimization, the API, tests, and a README — submittable on its own, since it demonstrates all three assessment pillars even without a browser in front of it. Everything past that (the React CRUD, the Web shell, Docker) is the enhancement phase — real, worth finishing, but built on top of a foundation that already stands on its own rather than raced in parallel with it. See Timeline.

02 Goals

01 — DATABASE

Optimized stored procedure

A naive department-spend report measured slow at 25,000 rows, then a real optimization — indexing, set-based aggregation — measured fast. Same shape as the real work story it's drawn from.

02 — BACKEND

.NET REST API

Domain / Core / Api, DI throughout, Swagger. Owns all database access — the only project that touches AppDbContext.

03 — FRONTEND

React + MUI, MenuItem only

Full CRUD as one complete vertical slice, not a partial dashboard. Rebuilds a real legacy problem — hardcoded Web.sitemap + asp:Menu — as an actual data-driven menu.

04 Architecture

Five .NET projects plus a client folder with two independent React bundles — solution layout below, full rationale in architecture.md. Application and Infrastructure are deliberately one project: this isn't a microservice split, there's one database, and a provider-swap abstraction would be fiction when the centrepiece is a SQL Server–tuned stored procedure.

EquipmentAcquisition.Domain          entities, enums
EquipmentAcquisition.Core            DbContext, repositories, services,
                                     DTOs, interfaces
EquipmentAcquisition.Api             Web API — owns all DB access
EquipmentAcquisition.Web             serves shell pages + static bundles
EquipmentAcquisition.Tests           xUnit + Moq

client/nav                    React+MUI — dynamic menu, own bundle
client/menu-admin             React+MUI — MenuItem CRUD, own bundle

  • Cache orchestration — queue table + BackgroundService + refresh proc, design resolved
  • Application + Infrastructure merged into Core

  • Employee added — wired to Requested/Approved By only

Foundation — done

  • Real solution scaffold — 5 projects, EF Core models, migration applied & verified live
  • Bogus seeding via SqlBulkCopy — 25,000 requests, ~7s, verified against the DB
  • Naive vs. optimized report proc — 642 → 6 logical reads, real Index Seek confirmed
  • Cache orchestration — queue (id-only), usp_RefreshAcquisitionDetailCache, DetailCacheRefreshWorker — live-verified end to end (rename → auto-refresh, ~2s, zero manual steps)
  • AuditTrail wiring — live-verified (Insert/Update/Delete rows captured correctly)
  • Full CRUD, all 7 acquisition-domain tables + MenuItem — a scope reversal from the original read-only plan, see table-design.md
  • Paginated/filterable grid + department-spend report endpoints, both live-tested
  • 19 passing xUnit tests (Moq) — MenuItem cycle detection, Vendor queue/audit wiring, AcquisitionRequest approve/reject state machine
  • README v1 — the submittable checkpoint

Enhancement — done

  • Web shell — AppBar + Drawer, nav-root/content-root, dev static file wiring to client/dist
  • React nav + menu-admin bundles — Webpack multi-entry, shared vendor chunk, full CRUD, verified with a real headless-browser test (Playwright), not just reviewed
  • Docker — Dockerfiles for Api and Web, 3-service compose (sqlserver/api/web), full docker compose up --build verified live, Swagger reachable, migrations apply on startup
  • README v2 — Docker as its own section, local-dev section, DB access instructions, port-conflict note

Beyond the original plan

  • Vendors / Departments / Equipment Categories admin pages — same list + shared FormDialog pattern as menu-admin, each its own bundle, each menu entry activated
  • Acquisition Requests page — paginated/filtered grid reading EquipmentAcquisitionDetailCache directly, approve/reject workflow, inline Purchase Order create/edit/remove on Approved rows
  • GET /api/purchase-orders/by-request/{id} — added to back the Requests page's inline PO lookup without ever fetching the full PurchaseOrders table
  • Two real bugs found and fixed via end-to-end Playwright verification, not caught by code review alone: a date filter binding to midnight, and a UI reload racing the cache-refresh worker's 2s cycle (resolved with an explicit Refresh action + notice, not a timer guess)
  • Asset Registry page (/assets) — paginated CRUD grid, own GET /api/assets/grid endpoint. Purchase Order selection is a debounced (350ms) live-search Autocomplete against GET /api/purchase-orders/grid?PoNumber= (full detail per option — PO number, vendor, qty, total) rather than a bounded picker, since PurchaseOrders (~15k rows) has no small "eligible" subset the way Approved-without-PO requests did for the Purchase Orders page's own picker
  • Department Spend Report page (/reports/department-spend) — read-only frontend for the optimized stored proc, the actual centerpiece deliverable; date range + optional department filter, sorted by spend with a grand-total row
  • AcquisitionRequest delete changed from a physical row removal to a soft delete (IsDeleted, mirrored into the cache table) — a request already carries approve/reject history and an audit trail, so retiring it from view is the right default, not erasing it. Same fix surfaced a second, unrelated bug: seed-data dates for Approved/Rejected/OrderDate/AcquiredDate compounded forward without ever clamping to "now," so a meaningful fraction of rows were dated in the future — fixed in the seeder and cleaned up on the live data
  • Purchase Orders page (/purchase-orders) — a deliberate reversal of the earlier no-standalone-page call: a second, standalone entry point onto PurchaseOrder (paginated, optional Vendor/AcquisitionRequestId filters, own GET /api/purchase-orders/grid) alongside, not replacing, the Requests page's inline per-row action. Its Create dialog picks the request from a dropdown of Approved/no-PO-yet requests (full detail per option — item, department, requester, qty, cost), not a typed id
  • PurchaseOrder also made soft delete (same reasoning as AcquisitionRequest), via an EF Core global query filter rather than manual per-method filtering — catches the AcquisitionRequest.PurchaseOrder navigation-property path a manual filter would have missed. AcquisitionRequestId's unique index is now filtered (WHERE IsDeleted = 0) so a replacement PO can be created after the old one is removed; VendorRepository's delete guard explicitly bypasses the filter, since a soft-deleted PO still physically blocks deleting its Vendor at the DB level
  • PoNumber changed from typed input to server-generated (PO-{year}-{id:D6}, same format the seeder uses) — a duplicate PoNumber was reproduced live (raw 500, same bug class as the DateTime.MinValue crashes), and removing the typed field eliminates the possibility structurally rather than validating against it
  • Test suite grown from 19 to 33 passing — added PurchaseOrderServiceTests (10 cases: validation branches, PoNumber generation, soft delete) and ReportServiceTests (3 cases, the From/To nullable-validation fix), closing a real gap where PurchaseOrderService had no coverage at all
  • Home page (/) — replaced the default Razor template placeholder with a real landing page: a Pending Requisitions by Department widget (every department, including zero-pending ones), shown only while the Acquisitions > Requests menu entry is active. Reads the same MenuItem.IsActive flag the nav itself reads, just from a second bundle — one flag gating both whether /requests is reachable and whether anything referencing it renders. Tenth React bundle
  • Bulk approval on the Requests grid — checkbox column (Pending filter only), toolbar action, and a new POST /api/acquisition-requests/approve-batch that's genuinely all-or-nothing: every id validated as existing-and-Pending before anything mutates, then every request update + audit row + cache-refresh signal committed in one SaveChangesAsync(), unlike the three-separate-saves pattern the single-row Approve/Reject/Delete paths already accepted. Verified live: a 3-row approval landed with one shared timestamp across the audit rows, and a batch containing an already-approved id was rejected in full (409, nothing persisted)
Next up: every sidebar entry now has a working page behind it. What's left is polish, not new scope — e.g. Purchase Orders staying a per-row action rather than a standalone list is a deliberate call, not a gap (see architecture.md), and the same async-notification pattern used for the cache refresh queue could extend to real outbound alerts if that's ever wanted.
